# Preshot "Source / View / PDF / PPT WYSIWYG" design for image groups

**Status:** In progress / Canvas and PDF are implemented; PPT is still pending
**Goal:** After an image is resized, cropped, and composed inside the canvas view frame, PDF and PPT must both use the same resulting view while the original source file always remains unchanged.

## Terminology

- **Source**: the immutable image file imported into the project, together with its real pixel dimensions.
- **View**: the result the user sees inside an image group, jointly defined by the view-frame size and the source-image crop rectangle.
- **Rendered view**: the exported result generated by cropping the source according to the view; both PDF and PPT must use it, and it must match the canvas view.

## Current issue

Schema v10 images previously stored only:

```ts
{
  file,
  aspectRatio,
  frameWidth,
  frameHeight
}
```

That version used centered `object-cover` cropping on the canvas, while PDF used `containSize()` to show the full source image with blank margins. Schema v11 already added crop/source dimensions and made canvas/PDF share the same crop spec; the PPT adapter is still not implemented.

## Data model

Schema v11 makes crop data independent from screen pixels:

```ts
interface ReferenceImage {
  id: string;
  file: string;
  sourceWidth?: number;  // source image pixels
  sourceHeight?: number;
  aspectRatio: number;   // sourceWidth / sourceHeight
  frameWidth?: number;   // canvas logical pt
  frameHeight?: number;
  crop?: {
    x: number;           // normalized source coordinates 0..1
    y: number;
    width: number;
    height: number;
  };
}
```

`crop` represents the truly visible rectangle within the source image. It does not depend on canvas zoom, display DPR, PPT dimensions, or export resolution.

### Invariants

```text
0 <= x,y <= 1
0 < width,height <= 1
x + width <= 1
y + height <= 1
(crop.width * sourceWidth) / (crop.height * sourceHeight)
  == frameWidth / frameHeight
```

## Interaction semantics

| Action | Changes | Does not change |
|---|---|---|
| Drag image card | Image order | view/crop |
| Drag view edges | `frameWidth` / `frameHeight`, and recompute `crop` around the current focus | Source image |
| Drag inside the view | `crop.x` / `crop.y` | frame, source image |
| Zoom slider | `crop.width` / `crop.height` | frame, source image |
| View source image | Only opens the source lightbox | view |
| Reset source image | Restores frame to source aspect ratio and sets `crop = full image` | Source file |

Ordinary click still selects; double-click shows the full source image. It is recommended that dragging inside the image be interpreted as crop panning only after entering "Adjust view" mode, to avoid conflict with image reordering.

## Migration

When migrating schema v10 → the new schema:

1. Preserve `file/aspectRatio/frameWidth/frameHeight`.
2. Compute a **centered cover crop** from the source aspect ratio and frame ratio.
3. After migration, canvas visuals must exactly match the previous `object-cover` appearance.
4. Persist `sourceWidth/sourceHeight` after decoding source dimensions.
5. If decoding fails, derive a virtual source coordinate system from `aspectRatio`; do not silently fall back to contain.

## Unified rendering spec

The domain layer provides one canonical pure function:

```ts
interface ImageViewRenderSpec {
  source: { x: number; y: number; width: number; height: number }; // source px
  destination: { width: number; height: number };                  // target units
}

viewRenderSpec(image, destinationWidth, destinationHeight)
```

Canvas, PDF, and PPT must all call it. Adapters must not independently choose `contain`, `cover`, or recentering.

## Unified export pipeline

```text
source file + persisted view
  -> viewRenderSpec(source pixels, normalized crop, destination ratio)
  -> renderViewBitmap(target pixel density)
  -> PDF adapter embeds bitmap at slot x/y/w/h
  -> PPT adapter embeds the same bitmap at shape x/y/w/h
```

- PDF must no longer call the current `referenceImageDrawBox(...containSize...)`.
- The PDF slot and PPT shape determine only target size, not crop.
- The two adapters may produce different bitmap resolutions based on DPI, but source crop must be identical.
- Image compression in PDF/PPT may change encoding quality only, never the visible area.
- If PDF `drawImage` crop or OOXML `srcRect` is used directly, parameters must still come from the same `viewRenderSpec`, and pixel tests must prove equivalence with the bitmap path.

## PPT output

Using `pptxgenjs` as the PPTX adapter is recommended, with deterministic view rendering preferred:

1. `viewRenderSpec` converts normalized crop to source-image pixels `sx/sy/sw/sh`.
2. Use Canvas/Sharp to generate the view bitmap at 2× the target PPT slot pixel density.
3. Add that bitmap to the PPTX at exact `x/y/w/h`, with no secondary cropping.
4. Reuse the same render pipeline for the PDF adapter, removing the current `contain` mismatch.
5. Keep the source image in the project for lightbox viewing and future recomposition.

If later verification shows that PptxGenJS/OOXML `a:srcRect` is stable across all target Office versions, crop can be mapped directly to avoid re-encoding; both implementations must still share `viewRenderSpec`.

## Acceptance

- A 2000×1200 source image may yield 1:1, 4:5, 16:9, or any other view ratio.
- Canvas, PDF page screenshots, and real PowerPoint screenshots all use the same crop.
- Subject-focus positional error is no more than 1 px at the comparison screenshot size.
- Resize, pan, zoom, reset, reload, and undo/redo all preserve the view.
- Drag reordering does not change crop.
- Double-click always shows the full source image.
- Canvas screenshots before and after v10 migration show no visual difference.
- Neither PDF nor PPT ever reverts to contain-style blank margins or unintended recentering.
